## J-모드 (JIT, §5.1 계약) — B1~B10

### B1. 브라우저 글루(hosts/otter-glue-js) 실브라우저 수동 확인 미수행 — node --check 문법 검증만, CI 게이트 아님

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: 브라우저에 otter 엔진(wasm32 J-모드)을 배포하는 임베더 전원. 특히 참조 글루(otter-glue.mjs)를 그대로 복사해 쓰는 웹앱/확장 개발자. 네이티브(wasmtime) 임베더는 무관.
- **실패 시나리오**:
  - 글루의 잠재 결함(오탈자, import 네임스페이스 불일치, BigInt 변환 실수 등)이 어떤 CI에서도 걸러지지 않고 프로덕션 브라우저에서 첫 발현 — 발현형은 전 compile 실패(-1/-2) → 전 함수 sticky Refused → 침묵 영구 T0(결과는 정확하나 티어업 전면 상실). [o13 §14.3-1, §10 W-6 ⑥: node --check 통과가 검증의 전부, §8(c): 'CI 게이트 아님(수동 확인 문서화)']
  - 브라우저별 실거동 차이(grow-detach 후 buffer 재취득 타이밍, table.grow/set 의미론, 동기 컴파일 제한)가 네이티브 E2E로는 검증 불가 — Chrome 메인스레드 동기 WebAssembly.Module() 8MB 제한은 문서화된 캐비앗이지만 실측은 미수행 [o13 §5.4]. 대형 방출 모듈이 걸리면 -1 → Refused (이 경로 자체는 설계된 강등).
  - 글루는 §5.3-2′ 섹션 화이트리스트/start 금지와 §5.3-4 타입 검사를 MAY로 의도 생략(README 명기) — wasmtime 참조 shim(패널 #3에서 보안 결함 3건 수정)보다 경화 수준이 낮아, 백엔드 버그로 오염된 방출 바이트가 능동 element/data 세그먼트를 실었을 경우 공유 테이블 슬롯 침묵 리바인드/게스트 메모리 기입을 글루가 차단하지 못함 [hosts/otter-glue-js/README.md; o13 §5.3-2]. 시그니처 불일치는 첫 호출 결정적 trap → §2.4 폐기 경로(계약이 수용하는 형상).
  - [추정] 계약의 최종 권위가 네이티브 E2E뿐이므로, 브라우저 전용 회귀(예: 특정 브라우저 버전의 funcref 테이블 공유 거동 변경)는 릴리즈 후에야 임베더 리포트로 발견된다.
- **조기 탐지 신호**: 브라우저 콘솔에서 compile() 내부 예외 / 반환 -1n·-2n 계열; 엔진 tier_of()가 임계 초과 후에도 "wasm-emit"으로 전이하지 않음(침묵 T0의 유일한 조기 신호); 첫 호출 WebAssembly.RuntimeError(타입 불일치 trap). 네이티브 wasm-e2e는 그린인데 브라우저에서만 실패하면 이 항목.
- **완화/우회**: 배포 전 대상 브라우저(최소 Chromium+Firefox+Safari)에서 티어업 실증(tier_of 마커 확인)을 수동 스모크로 1회 수행; 글루를 수정하지 말고 참조본 그대로 사용 + keepAlive/재취득 규율 유지; 경화가 필요하면 README 안내대로 raw-byte 섹션 워크(화이트리스트) 추가; 티어업 없이도 동작은 정확하므로(T0) 기능 리스크는 성능으로 한정됨을 운영 계획에 반영.
- **재평가 트리거**: headless 브라우저 CI 레인 신설 또는 실브라우저 수동 확인 수행·기록 시(§14.3-1 해소); otter_jit 계약 버전 변경(§5.1 v1 → 협상 도입) 시; 글루에 기능 추가(화이트리스트 구현 등) 시 재심.

### B2. 에러 코드 -5(기능 비활성) 예약 상태 — wasmtime 참조 shim이 생산하지 않아 참조 픽스처 부재

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: 자체 호스트(§5.1 계약 구현)를 작성하는 서드파티 임베더; 정책적으로 동적 컴파일을 끄는 임베더; -5 처리 경로를 통합 테스트하려는 임베더.
- **실패 시나리오**:
  - 자체 호스트가 정책 거부를 -5로 반환해도 검증할 참조 shim 산출물이 없음 — wasmtime shim은 미배선을 임포트 부재(인스턴스화 시점 링크 실패, --no-otter-jit 모드)로 표현하므로 -5를 영원히 안 만든다 [o13 §5.1 '예약됨' 지위 확정, §14.3-2]. 차등 대조 불가로 자체 구현의 -5 경로가 미검증 상태로 출하될 수 있음. 단 엔진 측 처리는 모든 음수 동일(sticky Refused)이라 오작동으로는 이어지지 않음(부호만 규범).
  - 임베더가 '기능 꺼짐 = -5 수신'을 기대하고 통합 테스트를 짰다가, 실제(-shim 참조 형상)에서는 인스턴스화 자체가 unresolved-import로 실패해 테스트/진단이 어긋남 — 발현 시점이 런타임 compile 호출이 아니라 기동 시점으로 이동 [o13 §5.1].
  - 진단 세분값은 SHOULD일 뿐이라(-5 포함) 로그 기반 원인 분류 도구가 호스트별로 다른 코드를 보게 됨 — 브라우저 글루는 유일하게 bind() 미호출 상태에서 -5n을 생산(README 명기)하므로 wasmtime/브라우저 간 -5 의미가 미묘하게 다름 [hosts/otter-glue-js/README.md].
- **조기 탐지 신호**: 기동 시 unresolved-import 인스턴스화 실패(미배선 형상) vs 런타임 -5 수신(배선+기능오프 형상)의 구별 자체가 신호; 글루에서 -5n이 보이면 bind() 누락이 첫 용의자.
- **완화/우회**: 엔진 관점에선 부호만 보므로 임베더는 -5를 자유 반환 가능(계약 적합); 거부-경로 테스트는 shim의 --reject-compiles 모드(전 요청 음수 반환)로 대체; -5 의미는 §5.1 문안을 정본으로 문서 링크.
- **재평가 트리거**: otter_jit.version 협상 구현(§5.1 예약 임포트 활성화) 시; 참조 shim에 정책-오프 모드(-5 생산)가 추가될 때; 계약 v2 논의 시작 시.

### B3. §13-7 차용-수명 쌍대 불변식은 UB-클래스 — 테스트 불가, 리뷰-전용 보호

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: otter를 포크/벤더링해 otter-engine의 module_dispatch·tail_signal·스크래치(CompiledWasmFn) 경로나 otter-wasmemit 마셜링 lowering을 수정하는 개발자·다운스트림 임베더. 무수정 사용자는 v1.0.0-testing.1의 리뷰 완료 상태(W-3 수동 차용-창 리뷰 통과)를 그대로 물려받아 직접 영향 없음.
- **실패 시나리오**:
  - 수정자가 스크래치 버퍼로의 Rust 참조 형성 지점을 2곳(module_dispatch to_vec 창 + tail_signal extend 창) 밖에 추가하거나 복사-즉시 규율을 완화 → 자기재귀/중첩 컴파일드 콜에서 외부 활성화의 live &[Value] 아래 덮어쓰기 = rustc noalias/readonly 위반 = LLVM 수준 UB — 침묵 미스컴파일 가능, 크래시도 오답도 결정적이지 않음 [o13 §2.5, §13-5/7].
  - 핵심 함정: 이 결함은 차등 테스트가 원리적으로 못 잡는다 — 패널 #3 렌즈 B가 복사를 통째로 제거하는 뮤테이션으로 전 차등 스위트가 그린임을 실증했음(safe-Rust 관측 동치) [o13 §10 W-2 행, §14.3-3]. 즉 '테스트 다 통과했으니 안전' 판단이 이 경로에선 무효.
  - [추정] 방출 코드 측 불변식(유일한 기입 = 자기 스크래치) 위반도 동류 — 백엔드 lowering 수정 시 $args 경유 기입을 추가하면 동일 UB 클래스로, wasm 검증기·하네스 모두 통과한다.
- **조기 탐지 신호**: 기계적 조기 신호 없음(UB 클래스라는 것이 이 항목의 본질). 대리 신호: 해당 파일 diff에 스크래치/차용 창 관련 변경이 있는데 PR에 수동 차용-창 리뷰 기록이 없으면 적신호; 스크래치 참조-형성 지점 grep 결과가 2곳이 아니면 즉시 중단.
- **완화/우회**: 해당 코드 변경 시 W-3와 동일한 수동 차용-창 리뷰를 필수 게이트로 유지(리뷰 체크리스트 항목 — §14.3-3); 다운스트림은 이 경로를 패치하지 말고 업스트림 이슈로; 참조-형성 지점 2곳 인벤토리를 리뷰 산출물로 갱신 보존; §13-1(복사는 catch_unwind 안)·§13-5(as_mut_ptr 1회 채굴) 규범 준수.
- **재평가 트리거**: module_dispatch/tail_signal/CompiledWasmFn/마셜링 lowering을 건드리는 모든 변경(항목 정의상 매번); wasm 대상 차용 검사 도구(tree-borrows 기반 Miri류)가 이 형상을 기계 검증 가능하게 되면 리뷰-전용 지위 자체를 재심.

### B4. 진짜 wasm trap 후 엔진/인스턴스 폐기-전용 (계약 규범 §2.4) — clear_trap/재진입 UNDEFINED

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: J-모드 임베더 전원(브라우저+wasmtime), 특히 장수 세션·세션당 상태를 엔진 안에 쌓는 임베더. Rust 패닉(try_dispatch→Err(Trap)→clear_trap 회복, E2E-4 실증)과 달리 진짜 trap(call_indirect 타입 불일치, 널 funcref, unreachable 도달)에만 해당.
- **실패 시나리오**:
  - 잔존 백엔드 버그(사전검사·하네스를 뚫은 시그니처 불일치, $state 손상 → $trapblk 등)로 trap 발생 → 활성화 전체가 Drop 실행 없이 unwind → live RefCell 가드 영구 미해제 → 임베더가 trap을 잡고 같은 엔진에 재진입하면 다음 borrow에서 패닉 연쇄, 계약상 UNDEFINED [o13 §2.4, try_dispatch rustdoc(W-6 ③)]. 메모리 안전 위반은 아니나 세션 상태 무결성 상실.
  - 임베더가 O-10의 clear_trap 보장(RAII Drop 언와인드 실행)을 wasm trap에도 적용된다고 오해하고 회복 로직을 작성 → 그 보장은 Rust 패닉 언와인드 전제라 wasm trap에는 부적용 — 회복 코드가 프로덕션에서 미정의 동작 경로를 밟음 [o13 §2.4].
  - 폐기-전용이므로 trap 1회 = 세션 전체 사망: 엔진 안에만 있던 미체크포인트 상태는 전부 소실 — 폐기·재생성 비용을 설계에 안 넣은 임베더는 가용성 사고로 발현. [o13 §11 위험 8: '활성화 사망 + 상태 무결성 상실', 호스트가 trap 잡아 세션 종료가 계약].
- **조기 탐지 신호**: 호스트 측: wasmtime Trap(예: indirect call type mismatch/UnreachableCodeReached) 또는 브라우저 WebAssembly.RuntimeError가 방출 함수 호출 스택에서 발생; 엔진 측: trap 이후 재진입 시 RefCell already-borrowed 패닉이 나오면 이미 규범 위반 사용 중이라는 확정 신호.
- **완화/우회**: 호스트에서 trap을 잡으면 해당 엔진/인스턴스를 즉시 폐기하고 새로 생성(재사용 절대 금지); 세션 상태는 엔진 밖으로 외부화/체크포인트; 정상 운영에서 trap은 백엔드 버그이므로 발생 즉시 방출 바이트·함수 idx를 채집해 업스트림 보고; malformed bytecode 대비는 try_dispatch/clear_trap(패닉 경로)로 충분함을 구분해 문서화.
- **재평가 트리거**: 백엔드에 trap 진단 표지·상태 재구축 경로가 추가될 때; wasm 스펙/wasmtime이 trap의 catch 가능성을 바꿀 때(현재 exnref EH는 trap을 못 잡음 — §2.4); trap 실발생 리포트가 1건이라도 오면 '잔존 버그' 전제를 재심.

### B5. add-only 방출 인스턴스/테이블 슬롯 무한 누적 — 해제 경로가 계약에 존재하지 않음 (임베더 문서화로 처리)

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: 장기 실행 J-모드 임베더: 서버형 장수 프로세스, push_func로 함수를 계속 추가하는 동적 워크로드(REPL/플러그인 호스트류), 브라우저 장수 탭. 함수 집합이 고정된 단명 프로세스는 사실상 무관(함수당 compile 정확 1회 — E2E-5 실증 — 라 누적이 핫 함수 수에 유계).
- **실패 시나리오**:
  - 함수를 무한정 push_func하는 워크로드에서 티어업마다 호스트 측 인스턴스 영구 보관(keepAlive/Vec) + 테이블 슬롯 grow가 단조 증가 — 해제 규범이 계약에 없어(§5.3-6 '영구 보관, 해제 없음') 호스트 메모리가 워크로드 수명 동안 순증 → 최종적으로 OOM 또는 table.grow 실패 [o13 §1 add-only 불변식, §11 위험 11, §14.3-6].
  - 자원 고갈의 발현이 오진 유발: table.grow 실패는 -4인데 §5.1이 '-4의 빈발 원인 = --growable-table 누락'으로 안내하므로, 누적-고갈로 인한 -4를 임베더가 링크 플래그 문제로 오진할 수 있음(§5.1도 '자원 고갈로 오독 금지'를 역방향으로만 경고). -4 → 해당 함수 sticky Refused → 이후 신규 티어업만 침묵 상실, 기존 방출 함수는 계속 동작.
  - [추정] 신뢰 경계가 있는 다중 테넌트 임베딩에서 게스트 바이트코드가 대량의 핫 함수를 의도적으로 만들면 호스트 메모리를 함수 수에 비례해 강제 점유 — t2 임계·compile 1회/함수 제약으로 속도는 제한되나 상한은 없음.
- **조기 탐지 신호**: 호스트 RSS 단조 증가; 인스턴스 보관소 길이(keepAlive.length / shim Vec len)와 __indirect_function_table.length의 단조 증가; HOST-COMPILE-COUNT 계수 증가 추세; 링크 플래그가 확실히 정상인데 늦게 -4가 나오기 시작하면 고갈 신호.
- **완화/우회**: 함수 수 상한/쿼터를 임베더가 부과; 장수 세션은 주기적으로 엔진+메인 인스턴스 전체를 재생성(전면 폐기가 유일한 회수 경로); 인스턴스 수·테이블 길이를 운영 메트릭으로 노출; 동적 함수 유입이 없는 형상으로 설계(고정 모듈)하면 누적은 유계.
- **재평가 트리거**: 계약에 슬롯 재사용/모듈 언로딩/약참조 보관이 추가될 때(현재는 add-only 불변식과 충돌 — otter-engine add-only 규율 자체의 재설계 필요); 실운영에서 -4 고갈 사례 첫 보고 시 진단 문서(-4 원인 2분법)를 3분법으로 갱신.

### B6. J-모드 게스트는 §7 nightly 핀 파이프라인(-Zbuild-std + EH 플래그) 상시 의존 — 분기 1회 범프 절차 유지 의무

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: wasm 배포 게스트(J-모드)를 빌드하는 임베더 전원 + 그 빌드 파이프라인을 7-10년 유지해야 하는 운영 주체. 소스는 stable-호환이지만 배포 아티팩트 빌드만 nightly-2026-08-31 핀(A-모드 산물만 이 파이프라인 밖). 네이티브 임베더 무관.
- **실패 시나리오**:
  - 임베더가 stable로 게스트를 빌드 시도 → O-12 compile_error!/링크 실패로 즉시 차단(안전한 실패) — 또는 §7 전제(rust-src, nightly측 wasm32-wasip1 타깃) 누락 시 EH와 무관해 보이는 링커 실패(crt1-command.o/-lc/-lunwind)로 발현해 원인 추적이 어려움 [o13 §7 빌드 전제].
  - 핀 범프 시 업스트림 드리프트로 파손: exnref 디폴트 재반전(산물 비트 변화), LLVM legacy-eh 옵션 제거로 -Cllvm-args가 하드 에러화, build-std/wasip1-EH 파손 — §7.1 범프 절차(비트-diff 3분기, try_table 스모크)가 이를 게이트하지만 분기 1회 절차를 수행할 인력·규율이 끊기면 핀이 사실상 동결되어 보안 패치된 툴체인으로 이동 불가 상태가 됨 [o13 §7.1].
  - 날짜 nightly 아카이브(static.rust-lang.org/dist/2026-08-31/)의 보존은 계약 보장이 아님 — 소실 시 미러 부재 상태라면 빌드 재현 불능(현재는 '리스크 현실화 시 미러+rustup toolchain link' 방침만 고정, 절차 미실행) [o13 §7.1 핀 지속가능성].
  - 카나리아 레인(wasm-eh-latest-nightly-canary) 적색을 머지 차단으로 오독하거나, 반대로 장기 무시하면 강제 범프 시점에 누적 파손을 한꺼번에 맞음 — 카나리아 적색 = '범프 절차를 일정에 올리라'는 신호가 정확한 해석 [o13 §7.1 CI 2레인].
- **조기 탐지 신호**: wasm-eh-latest-nightly-canary 레인 적색(조기 신호의 정본); just wasm-eh-smoke/wasm-demo-build 실패; 범프 절차 2단계 비트-diff에서 산물 상이(디폴트 재반전 신호); stable 빌드 시도 시 compile_error! 발화는 정상 차단이지 버그 아님.
- **완화/우회**: 핀 값의 단일 정본(justfile wasm-nightly)만 수정하는 §7.1 범프 절차를 분기 1회 캘린더에 고정; 컴포넌트 타르볼 4종의 외부 미러를 지금 선제 확보([추정] 방침만 있고 미실행이므로 저비용 선행 권장); nightly 수용 불가 임베더는 A-모드(빌드타임 compile_module AOT) 경로로 우회; --no-otter-jit/feature-off 형상은 T0로 동작하므로 긴급 시 T0-only 배포가 폴백.
- **재평가 트리거**: rustc가 wasm32-wasip1의 unwind std를 stable로 출하(-Zbuild-std 불요화)하면 항목 자체 소멸; O-12 게이트 완화((b)안)를 오너가 재상정하면 재심; 카나리아 적색 발생 시마다; O-13 stable-게이트 오픈 질문(핀 정책) 오너 결정 시.

### B7. 헬퍼 트랩 vs 산물 가드 트랩 진단 구분 불가 — 둘 다 UnreachableCodeReached

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: A-모드(compile_module AOT → 정적 링크/컴포넌트) 산물을 운영하는 임베더의 장애 triage 담당자. J-모드도 trap 종별 진단이 없는 점은 동일하나(§2.4는 폐기만 규정) 이 항목의 정본 실측은 A-모드 [o16c-spike-results B4/§4-6, o16c-design:291].
- **실패 시나리오**:
  - 프로덕션에서 UnreachableCodeReached trap 발생 → 원인이 (i) 헬퍼의 문서화된 fail-stop 패닉(OOB 태그/정수 Div unreachable!/미지 unop 태그 = 방출기 버그의 결정적 발현) 인지 (ii) 산물 가드 트랩($state 손상 등)인지 trap 종만으로는 판별 불가 — 방출기 버그를 데이터 문제로 오분류하거나 그 역으로, 근본원인 분석이 지연됨 [o16c-spike-results §4-6: '진단 구분 필요 시 O-16c′에서 헬퍼 트랩 전용 표지 검토' — 의도적 비목표 존치].
  - 동작 자체는 오답이 아님: 실측상 트랩은 결정적이고 A-모드에선 트랩 후 인스턴스 생존·후속 호출 정상(O-12 규율의 올바른 발현) — 피해는 진단 시간에 한정 [o16c-spike-results B4].
- **조기 탐지 신호**: 산물 모듈발 UnreachableCodeReached 자체가 이 항목의 발동 신호(정상 운영에선 도달 = 버그); wasmtime 백트레이스의 함수 인덱스/코드 오프셋을 방출 레이아웃과 대조하면 수동 판별 가능 [추정 — 문서에 절차 없음, 오프셋 대조는 일반 wasm 디버깅 관행].
- **완화/우회**: trap 재현 입력을 T0(인터프리터)로 재실행 — 헬퍼 패닉 형상이면 T0에서 같은 지점 패닉으로 분리 판별; 트랩 위치(함수/오프셋)를 로그에 보존해 업스트림 보고; 구분이 운영상 필수라면 O-16c′ 표지 export를 요구사항으로 제기.
- **재평가 트리거**: O-16c′(진단 표지 export — 헬퍼 트랩 전용 별도 trap 함수) 착수 결정 시 항목 소멸; b′ 표면 확장 재심 시 함께 재검토(o16c-design:291이 명시한 재심 조건).

### B8. 호스트의 memory64-형상 모듈 방어는 Instance::new 한 겹(-2 클래스) — 핀 테스트로 고정

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: J-모드 wasmtime 참조 호스트(otter-host-wasmtime) 사용/포크 임베더. 방출 바이트는 엔진이 생성하므로 memory64 형상 유입 경로는 백엔드 버그 또는 shim 앞단 오염뿐 — 정상 운영자는 방어선 구조만 인지하면 됨.
- **실패 시나리오**:
  - 방어가 단층: §5.2 화이트리스트는 섹션-id만 검사해 i64 memory 임포트를 통과시키고, wasmtime 48은 memory64를 기본 수용해 Module::new(파싱/검증)도 통과 — 유일한 하중 층은 Instance::new의 임포트 타입 불일치(-2). 핀 테스트 memory64_shaped_module_is_refused_at_instantiation_not_parse(hosts/otter-host-wasmtime)가 3사실(파싱 통과·화이트리스트 통과·인스턴스화 거부)을 고정 [o19-wasm64-design:169, 마감 리뷰 F1 정정].
  - wasmtime 범프가 임포트 매칭을 완화하면 핀 테스트가 시끄럽게 발화하도록 설계됨 — 그러나 핀 테스트를 무시/삭제하고 범프하는 포크 임베더는 방어선 소멸을 모른 채 진행 [o19:169]. [추정] 그 경우 memory64-형상 버그 산물이 인스턴스화까지 성공하면 32비트 주소 전제(스크래치 베이킹 등)와 어긋나는 미정의 형상이 됨.
  - 진단 함정: 이 형상의 -2는 §5.1이 안내하는 -2 빈발 원인('링크 플래그 전누락/--export-table 누락')과 같은 코드라, 백엔드 버그로 memory64 형상이 나왔을 때 임베더가 링크 플래그만 뒤지며 오진할 수 있음(원문 기대값 -1이 오류였을 만큼 직관과 어긋나는 클래스 배정) [o19:169].
- **조기 탐지 신호**: 링크 플래그가 검증된 환경에서 재현되는 -2가 나오면 방출 바이트를 wasm-tools로 덤프해 memory 임포트 addrtype 확인; 호스트 트레인 범프 CI에서 해당 핀 테스트 적색 = 임포트 매칭 완화 신호(이 항목의 설계된 조기 경보).
- **완화/우회**: 핀 테스트를 호스트-트레인 범프 게이트(§7.1 절차)에서 절대 제외하지 않기; 포크 호스트는 화이트리스트를 섹션-id 검사에서 임포트 타입-레벨 검사로 자체 강화 가능(계약상 -1 거부 MAY와 정합); 방출측은 §13-3 cfg 조임(target_arch=wasm32)이 wasm64 오방출을 원천 차단.
- **재평가 트리거**: wasmtime 버전 범프 때마다(핀 테스트가 자동 재심); 엔진-on-wasm64 J-모드 백로그(O-19 '조건부 — 게이트 밖')가 채택되어 memory64가 정당 형상이 되는 순간 방어선 전체 재설계; §5.2 화이트리스트 사양 변경 시.

### B9. O-17 잔여: sharedness 자기-탐지 맹점(V3 과소/V1 과잉) + atomics∧bulk-memory 불가(wasi-libc TLS 충돌)

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: 공유 선형 메모리(+atomics) 게스트를 빌드하는 고급 임베더(v1.1 옵트인 형상, L0 수동 링크-호환 — 단일 에이전트 실행 규범). 기본(비공유) 형상 임베더는 무관.
- **실패 시나리오**:
  - V3(과소 탐지): shared 메모리인데 +atomics 없이 빌드된 게스트 — cfg!(target_feature="atomics") 컴파일타임 자기-인지가 비공유로 오판 → 방출 모듈이 비공유 (memory 0) 임포트 → sharedness 정확-일치 검사(limits 서브타이핑은 shared↔unshared 무강제)에서 인스턴스화 실패 → -2 → sticky Refused → 영구 T0. 동작은 정확, 티어업만 침묵 상실 — '미스컴파일은 절대 아님'이 코드 주석에 명문 [crates/otter-engine/src/lib.rs:752-763, o13 §5.2 v1.1].
  - V1(과잉 탐지): +atomics로 컴파일됐지만 비공유로 링크된 게스트 — shared 형상 임포트를 방출 → 동일하게 -2 → 영구 T0. 의도된 맞바꿈(탐지 신호를 컴파일타임 1개로 유지하는 대가)으로 문서화됨 [동일 소스 주석: 'BOTH degrade ... a tier-up loss, never a miscompile'].
  - +bulk-memory 불가: atomics∧bulk-memory 조합은 LLVM이 std의 #[thread_local] errno에 진짜 TLS 재배치를 방출해 프리빌트 단일스레드 wasi-libc의 .bss errno와 충돌(R_WASM_MEMORY_ADDR_TLS_SLEB 링크 에러) → 공유 게스트에서 bulk-memory 의존 기능을 쓰려는 임베더는 빌드 자체가 불가. 정본 레시피는 -bulk-memory를 load-bearing으로 명시 [justfile:61-75 wasm-atomics-rustflags]. 해소는 커스텀 wasi-libc(L2 묶음)로 이월 — 미착수 [소스 주석의 'unblock conditions' 및 과업 기술; 정본 otter-o17-shared-memory-l0.md는 .claude-research-library/에 동기화되어 있음].
- **조기 탐지 신호**: shared 빌드에서 링크 플래그가 정상인데 전 compile이 -2로 실패하고 tier_of가 영원히 T0 → V1/V3 오탐지 신호(방출 바이트의 memory 임포트 shared 여부를 실제 메모리와 대조하면 확정); +bulk-memory 추가 시 R_WASM_MEMORY_ADDR_TLS_SLEB 링크 에러는 이 항목의 결정적 시그니처.
- **완화/우회**: 정본 §7 atomics 레시피(justfile: +atomics,-bulk-memory,+mutable-globals + --shared-memory)만 사용하고 플래그 조합을 손수 변형하지 않기 — 정본 레시피에선 atomics 플래그와 sharedness가 항상 동행해 V1/V3이 발생하지 않음; bulk-memory가 필요하면 공유 메모리를 포기하거나 커스텀 wasi-libc(L2) 완료 대기; 성능 민감 배포는 티어업 마커를 기동 스모크에 포함해 침묵 T0를 조기 검출.
- **재평가 트리거**: 커스텀 wasi-libc(L2 묶음) 착지 시 bulk-memory 항 소멸+V-형상 재실측; wasi-libc 업스트림이 스레드-대응 프리빌트를 출하할 때; sharedness 탐지를 컴파일타임 cfg!에서 링크-산물 introspection으로 바꾸는 변경 제안 시; wasi-threads 후속(현재 금지 트랙) 재개 시.

### B10. 네이티브 AOT(CallMode::Table) 예외 존속(오너 기결정): TailCall unimplemented! + table[callee] 무범위검사

- **심각도(testing 실사용)**: 상 (high)
- **영향 대상**: otter_baseline/otter_cranelift의 compile_module을 네이티브 정적 제품으로 직접 쓰는 임베더(ModuleEngine 미경유 — 디스패처·티어 없음). ModuleEngine(Dispatch) 사용자와 wasm A-모드 사용자는 무관(각각 OOB→fill 폴백/명시 가드 보유).
- **실패 시나리오**:
  - TailCall이 포함된 모듈을 CallMode::Table로 컴파일 → unimplemented! 패닉(컴파일 타임) [crates/otter-cranelift/src/lib.rs:1001, crates/otter-baseline/src/lib.rs:847] — 빌드 파이프라인 하드 실패. 메커니즘 부재가 근본 원인(디스패처 없는 직접 호출 경로라 O-8c 트램폴린 적용 불가)으로 오너가 tier-parity 예외로 확정 [o8 §8.10, 2026-09-02 결정; W-6 소멸 부기가 '네이티브 예외는 별개 존속' 재확인].
  - 런타임 Call에서 callee 레지스터 값으로 table[callee]를 MemFlags::trusted() 로드 후 간접 호출 — 범위검사 없음 [otter-cranelift:1047-1052, baseline:894 동형]. callee가 OOB/음수(런타임 레지스터 값이라 check_func가 못 막음)면 테이블 밖 임의 주소 로드 → 그 값으로 간접 점프 = 임베더 프로세스 내 메모리 안전 위반·크래시·[추정] 임의 코드 실행 표면. 비신뢰 바이트코드를 이 경로에 넣으면 보안 노출이며, 신뢰 바이트코드라도 동적 callee 계산 버그가 곧장 wild jump. 대조: module_dispatch/T0/wasm A-모드는 전부 OOB→fill fail-closed(O-14 §3.1/§3.2a가 wasm 측을 전폭 가드로 경화) — 네이티브 Table 모드만 무가드로 잔존.
  - 패닉-없는 메모리 손상 클래스(O-12가 최악으로 규정)라 발현이 비결정적: 낮은 OOB 인덱스는 인접 힙 값을 fn 포인터로 오독해 침묵 오동작 가능 [추정 — 가드 부재의 일반적 귀결, 문서 실측은 wasm 측 M4(비가드 시 TableOutOfBounds trap)뿐이고 네이티브는 trap조차 없음].
  - Spectre-v1 가젯 후보 관점 병기(RELEASE-GATE 1차 평가 (b)클래스 처분 1): 무범위검사 `table[callee]` 로드는 '경계검사-부재 간접 분기' 형상이라 in-process 투기실행(v1-형) 가젯 후보이기도 하다 — 상위 검증 계층 부재는 코드로 확정(otter/src/lib.rs:1616-1622가 callee 값 검사를 명문 비목표로 선언, Table 모드는 디스패처 미경유). 수용 전제(신뢰 입력 한정)가 유지되는 동안만 수용 갭이며, 전제가 깨지면 아키텍처 OOB와 투기 채널 양면에서 즉시 재심(RELEASE-GATE (b) 반복 의무 (vi) 편입).
- **조기 탐지 신호**: TailCall 갭: 컴파일 시 unimplemented! 패닉 메시지로 즉시·명시적 검출. 무범위검사: 조기 신호 사실상 없음 — 호출 사이트 부근 segfault/비결정 크래시가 동적 callee 값과 상관되면 이 항목을 첫 용의자로; ASan/발레리 계열로 테이블 경계 밖 로드 검출 가능 [추정].
- **완화/우회**: 비신뢰·미검증 바이트코드는 절대 CallMode::Table에 넣지 않기(신뢰 경계가 있으면 ModuleEngine Dispatch 또는 wasm A-모드 사용 — 둘 다 fail-closed); callee가 정적으로 유계임을 임베더가 사전 증명(callee 레지스터에 상수만 유입되는 프로그램으로 제한)하거나 임베더 측 사전 검증 패스를 추가; TailCall 필요 프로그램은 Dispatch 모드로.
- **재평가 트리거**: 오너가 §8.10 네이티브 예외를 재상정할 때(예: cranelift return_call 기반 진짜 꼬리호출 설계 착수); Table 모드에 O-14형 명시 가드(fill 폴백)를 이식하는 변경 제안 시; 네이티브 Table 경로에 비신뢰 입력을 허용하려는 임베딩 요구가 처음 등장하는 순간(현 전제 붕괴 — 즉시 재심).

## A-모드 (AOT/컴포넌트) — B11~B17

### B11. p3 충족은 아키텍처-수준(실행 표면 = 2패키지 동기 함수 2개) — sync-WIT 한정, =50.0.1 핀 결박(semver-면제 표면; testing.2에서 48.0.1→50.0.1 이동)

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: J-모드 참조 호스트를 p3-bridge feature로 빌드해 WASIp3 서비스를 게스트에 공급하려는 임베더; 스트림 I/O·비동기 sockets·wait-* 등 async-WIT 기능이 필요한 임베더; p3-bridge 포함 호스트를 장기 배포·wasmtime 범프하려는 운영자.
- **실패 시나리오**:
  - async-WIT p3 임포트(wait-for류·스트림 I/O)를 배선 시도 → 동기 인스턴스화 거부 + 실패 시도 자체가 Store를 래치(latch-then-validate, o16f §1-S2-E5 실측) → 이후 모든 동기 진입점이 validate_sync_call로 거부 → otter_jit.compile 전건 -2 → 침묵 전면 T0 강등(o16f §4). 크래시 없이 성능만 조용히 붕괴하는 fail-open 클래스.
  - async 인스턴스화 후 동기-lift에서 블로킹하는 표면 호출 → "cannot block a synchronous task" trap으로 게스트 실행 중단(E5 실측).
  - "p3 충족"을 폭(breadth)-수준으로 오독: 실측 실행 표면은 wasi:clocks/monotonic-clock@0.3.0 + wasi:random/random@0.3.0의 동기 함수 2개뿐(o16f §8). cli/filesystem-types/sockets-types 등 화이트리스트-적격 동기 표면도 미실행이라 배선 시 미검증 경로를 밟는다 [추정].
  - wasmtime-wasi를 락 핀(현 50.0.1; testing.1은 48.0.1) 밖으로 범프 → p3 호스트 표면은 semver-면제 자기선언("not compliant with semver… Bug and security fixes limited to wasip3 will not be given patch releases", p3/mod.rs 축자) — API 파손·거동 변화가 예고 없이 발생 가능하고, 배포 호스트가 보안패치-비보장 실험 표면을 나른다(o16f §6).
- **조기 탐지 신호**: HOST-P3-STORE-SYNC-OK 래치 프로브 적색(매 실행 기계-고정); 티어업 계수 0 + 전 compile 반환 -2(전면 T0 강등 징후); "cannot block a synchronous task" trap; NEGPROBE-P3-UNWIRED-OK·just wasm-e2e-p3 게이트 적색; 범프 후 p3 모듈 컴파일/링크 에러.
- **완화/우회**: 브리지 표면을 §3-2 동기-WIT 화이트리스트 안으로 엄수(MUST); async-향 요소(async 호스트 함수 실링크·async limiter/call-hook/fuel-yield)를 게스트 Store에 절대 반입 금지; =50.0.1 락 핀 유지; p3 불요 배포는 스톡 빌드 사용(feature 격리 실측 — 표면 미컴파일); 매 testing/stable 릴리즈에서 업스트림 이슈 점검(§6 릴리즈 게이트); 자체 호스트 제작 시 래치 프로브를 이식.
- **재평가 트리거**: async-WIT 수요 발생(E4 전면 async 재배선 이행 — 선행 게이트 2건: Instance::new_async 규범화 + tokio 도입 영향 평가, o16f §5); wasmtime-wasi 핀 범프(S2 경계 실측 E5 재실행 의무); wasip3 rustup 프리빌트 std 출현(S1 재평가); 업스트림 p3 표면의 semver 준수 전환.

### B12. 역방향 프록시(컴포넌트→코어)는 미실측 — [추론]만 존재

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: 서드파티 컴포넌트의 world 임포트를 호스트가 받아 코어 otter 인스턴스(게스트 코드)로 되돌려 충족시키려는 임베더 — 즉 컴포넌트가 otter 게스트 기능을 소비하는 형상을 원하는 사용자.
- **실패 시나리오**:

  - 역방향 형상에는 게이트·프로브·E2E 마커가 전무 → 오작동(오답·trap·교착류)이 프레임워크 CI에 걸리지 않고 임베더 배포까지 침묵 통과 [추정].

### B13. 링크-후 바이트 게이트 원리적 불가(wasm-merge 재인코딩) — 방어선은 의미-수준 검증 + 오라클 차등뿐

- **심각도(testing 실사용)**: 중 (medium)

### B14. wasm-tools 1.246.2 핀의 TOFU 앵커 약함 — 업스트림 체크섬 미공표

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: 새 머신/CI에서 just wasm-aot-tools를 최초 실행하는 사용자; 핀이 x86_64-linux 타르볼 한정이라 로컬 재확립해야 하는 타 플랫폼 기여자; 공급망 감사를 요구하는 보안-민감 임베더.
- **실패 시나리오**:
  - 최초 확립 시점 오염: 업스트림이 체크섬을 공표하지 않아 SHA-256 핀의 근거가 자체 TOFU(독립 2-경로 다운로드 일치)뿐 — 2-경로가 공통 경로(동일 MITM/미러)로 오염되면 핀이 오염의 고정 장치가 되고, 변조된 wasm-tools가 strip/validate/embed/new를 수행해 출하 산물 바이트에 손을 댄다 [추정 — 개연 낮음, 교차 앵커 존재].
  - 타 플랫폼 기여자의 로컬 재확립이 더 약한 절차로 수행 → 기여자 간 도구 불일치 또는 나쁜 핀의 로컬 고착(불일치는 fail-closed지만 원인 추적 마찰, o16c §3.2 T-N4).
  - 업스트림 릴리스 타르볼 재발행(동일 태그·다른 바이트) → 핀 불일치로 조달 레시피 fail-closed 파손 — 가용성 문제(오염 아님).
- **조기 탐지 신호**: just wasm-aot-tools 해시 불일치 실패; 전개 직후 --version 단언 실패; 독립 경로 재다운로드 간 해시 상이; 시스템 PATH의 wasm-tools와 캐시 핀 도구의 버전/거동 차이(비-PATH 명시 호출이 차단).
- **완화/우회**: TOFU 절차 준수(① 독립 2-경로 해시 일치 ② 업스트림 체크섬 출현 시 대조 ③ 출처·일시 기록 — §3.2, L-3 확립 기록 2026-09-04 존재); 스파이크 보존 타르볼 교차 앵커; 캐시 경로 명시 호출(비-PATH) + --version 단언; SHA-핀 타르볼 외부 미러 방침(§9-1 4항); 타 플랫폼 재확립 시 동일 2-경로 절차 적용.
- **재평가 트리거**: 업스트림이 서명 체크섬/증명(attestation) 공표 시작; wasm-tools 핀 범프(§5.6 뮤테이션 전건 재실행 동반 의무); 타 플랫폼 타르볼 핀 추가; 릴리스 아카이브 소실 징후.

### B15. WIT 정본은 게이트 corpus 귀속 — 일반 제품엔 산물별 WIT 생성 단계 필요

- **심각도(testing 실사용)**: 중 (medium)
- **영향 대상**: calc 형상(h_add7/hc_xor) 밖의 자기 host 함수 집합을 가진 산물을 컴포넌트화하려는 임베더 — 즉 게이트 코퍼스 형상이 아닌 host-포함 제품 전부.
- **실패 시나리오**:
  - 자기 host-포함 산물을 컴포넌트 체인에 투입 → 정본 wit(hosts/otter-aot-link/wit/aot-artifact.wit)의 aot-artifact-host 월드는 게이트 코퍼스 calc의 h-add7/hc-xor만 선언(파일 축자: "Import lists mirror the gate corpus manifest's otter_host set; a per-product WIT generation step is out of scope") → 잔존 otter_host.* 임포트가 월드와 불일치해 component new가 시끄럽게 거부 — fail-closed지만 컴포넌트화 자체가 막힘.
  - 임베더가 산물별 WIT를 수작성 → $root 모듈-문자열 + kebab 개명 규약(§6.1 실측)·canonical ABI 하강 정확일치를 손으로 재현해야 하며, 실수 시 embed/new 단계 거부로 발현. 하강 타입-청결성의 실측 범위는 i64/i32 스칼라 시그니처(O-14 §2.2 계약 내)라 계약 내 형상이면 한정적이나, 수작성 자체가 규약 누수 지점.
  - host-프리 월드(aot-artifact)를 host-포함 산물에 오적용 → 잔존 임포트 미해소로 component new 거부(시끄러움, E11 클래스).
- **조기 탐지 신호**: component new의 임포트/export 불일치 에러("failed to find export of function `otter-entry`"류 포함); §6.2 빈-world/world-불일치 네이티브 검사 적색; 잔존-임포트 정확일치(=) 게이트 적색 — 전부 산출물-없는 fail-closed.
- **완화/우회**: 현재는 컴포넌트 형상을 host-프리 산물(엔트리 시그니처 고정이라 정본 aot-artifact 월드가 임의 산물에 유효) 또는 게이트 코퍼스 형상에 한정; host-포함 제품은 코어-결합 배포 형상으로 서빙(WIT 불요 — o16c §2-4 폴백 형상과 동형); 필요 시 §6.1 규약($root+kebab, 동기 스칼라 시그니처)을 따라 산물별 WIT 수작성 후 전 체크 체인 + 오라클 차등 통과 확인. 컴포넌트 형상 엔트리는 argc=0/게스트-부트 한정(§6.1)임도 병행 유의.
- **재평가 트리거**: 산물별 WIT 생성 단계(사이드카 manifest → WIT 방출기) 구현; host-포함 컴포넌트의 프로덕션 수요 발생; wasm-tools 핀 범프로 $root/kebab 결부 규약 변동 시(§5.6 재실행에서 판명).

### B16. A64 산물은 링크 체인 진입 불가(승인 형상 = pre-link + 호스트 직접 헬퍼 임포트), shared×memory64 거부, A64 사이드카 거부

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: memory64(wasm64) AOT 산물에 정적 링크(b′ 헬퍼)·사이드카 매니페스트·컴포넌트화·shared memory 중 하나라도 함께 원하는 임베더 — 실질적으로 4GiB+ 힙 지향 사용자 전부(v1 전-헬퍼 정책이라 헬퍼-무 프로그램은 사실상 없음, o19 §2.5).
- **실패 시나리오**:
  - A64 산물을 링크 체인에 투입 → facts.rs:206 owned_memory에서 fail-closed 거부(실측 S2-M3). 근본 원인은 wasi-libc wasm64 부재(외부 블로커)로 A64×b′ 정적 링크 자체가 차단 — 승인 형상은 pre-link 산물 + 호스트 직접 헬퍼 임포트(otter-aot-e2e 네이티브 스텁, S2-M4 실증)뿐.
  - shared×memory64 조합 요청 → AotOpts 검증 단계 fail-closed 거부(SHARED_MEMORY_IMPORT_MAX_PAGES가 wasm32 전용 상수 — 별도 실측 전까지 거부, o19 §2).

- **조기 탐지 신호**: 전부 시끄러운 fail-closed 에러: L-2 owned_memory 거부, AotOpts shared×A64 거부, emit-aot 사이드카 명시 에러, record==live 게이트의 memory64 바이트×구/false manifest 거부, J-모드 인스턴스화 -2(파싱은 통과하므로 -2가 늦게 나오면 이 항목 의심). 핀 테스트 memory64_shaped_module_is_refused_at_instantiation_not_parse가 3사실 고정.
- **완화/우회**: A64는 승인 형상(pre-link + 호스트 직접 헬퍼 임포트)으로만 사용; 링크·사이드카·컴포넌트·shared가 필요한 워크로드는 wasm32 유지; 4GiB+ 실수요는 데이터 분할·호스트-측 메모리 관리로 우회 [추정 — 정본 외 일반론].

### B17. wasm64 성능 음수(w64/w32 ≈1.45×, 현행 로그 단일값 1.47×) — 게이트 근거는 성능이 아니라 스코프 결정

- **심각도(testing 실사용)**: 하 (low)
- **영향 대상**: "64-bit이 더 낫다"는 직관이나 4GiB+ 힙 기대로 memory64를 켜려는 임베더; O-19 게이트 통과를 성능-검증으로 오독하는 평가자; 벤치마크 작성자.
- **실패 시나리오**:
  - 4GiB+ 실수요 없이 memory64 활성 → guard-page 생략 불가로 명시 bounds check가 붙어 T0 디스패치 루프 실측 wasm32 356ms vs wasm64 523ms(w64/w32=1.47×, run-final.log 단일값 — v1의 "1.45–1.47×" 밴드 하한은 현행 로그로 검증 불가) + 크기세 +8.55%(37181/34253) — 이득 0에 처리량·크기 회귀만 감수.
  - O-19 완료를 wasm64 프로덕션 레인으로 오독: 게이트 근거는 성능이 아니라 오너 스코프 결정("형상 가능 실증 + 폭 전제 파라미터화")이며, A64는 벤치 기본 레인 불포함 [결정] — A64 경로의 성능 회귀가 기본 벤치에서 검출되지 않음.
  - wasmtime memory64 default-ON(48.0.1/45.0.3 실측)을 계약으로 오인: config.rs:1220 문서는 여전히 "false by default" 선언(문서-실측 괴리) — 기본값 재반전 시 명시 옵트인 없는 임베더 코드가 조용히 거동 변경(o19 §8-1).
- **조기 탐지 신호**: memory64 활성 후 처리량 1.2–1.8× 밴드 하락(문서 밴드) 및 산물 크기 ~8.5% 증가; 자기 워크로드의 w32/w64 이중 방출 차등 실행(기존 differential 하네스 패턴)으로 직접 비교 가능; 정확성 문제는 아님(modulo-addrtype 차분 게이트가 값 동일성 보증).
- **완화/우회**: 기본 wasm32 유지, memory64는 4GiB+ 워킹셋 실증 시에만 옵트인; 채택 전 자기 워크로드로 양 폭 벤치; 호스트 코드에 명시 wasm_memory64(true) + 음성 대조(명시 false → A64 거부) 규율 유지(기본값 재반전 방어, o19 §4); A64 게이트 통과를 성능 주장에 인용하지 않는다.
- **재평가 트리거**: 엔진의 memory64 bounds-check 최적화(밴드 축소)로 성능세 재실측 필요 시; 4GiB+ 실수요 발생; wasmtime memory64 기본값 재반전(음성 대조가 발화); A64를 벤치 레인에 편입하는 결정.
